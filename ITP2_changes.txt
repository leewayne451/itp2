[2026-11-13 SGT]  CHANGE 011 — New-hire journey tracker with smart appointment booking
-------------------------------------------------------------------------------
Summary
  The employee a request is about gets a tracker like a parcel-delivery page: every step,
  who it is waiting on (by name), an estimated date per step and for the whole request, and
  the EUSS appointment with what to bring. Appointments are matched to free EUSS slots
  automatically as soon as IT processes the request, so nobody has to arrange a time by
  e-mail. The employee or requestor can move it to another free slot; when EUSS blocks a
  slot, everyone in it is moved to the next free one and told.

What changed
  services/backend/app/tracker_logic.py  NEW, pure (no DB): EUSS roster -> slots, the slot
                                      choice (free place, >= lead time, no clash with the
                                      person's other appointment, bundled next to it when
                                      possible, else earliest), what to bring per request
                                      type, the tracker steps / owners / estimates, office-hours
                                      rounding of estimates
  services/backend/app/scheduling.py  NEW: roster top-up, free-slot query, atomic booking
                                      (slot row locked: a slot can never go over capacity),
                                      auto-book, reschedule, block / re-open with re-matching,
                                      appointment e-mail, tracker data (uses the Analytics
                                      stage statistics of CHANGE 007 when there is history)
  services/backend/app/api/tracker.py NEW endpoints: /api/tracker/me, /api/requests/<id>/tracker,
                                      /slots, /reschedule, /api/euss/slots (+ add, block, reopen)

Decisions
  - Slots are 30 min, Mon-Fri 09:00-12:00 / 14:00-17:00 SGT, 2 desks, opened 21 days ahead,
    and a request is never booked less than 24 h after IT processes it (EUSS needs time to

  - A slot's places count only bookings of requests still waiting for EUSS, so a request
    closed any other way frees its place without extra code.
  - Public holidays are not in the roster: EUSS blocks those slots (bookings move automatically).

[2026-11-08 SGT]  CHANGE 009 — Separation of duties: no self-approval
-------------------------------------------------------------------------------
Summary
  A user can no longer approve, reject or process a request whose target employee is
  themselves. The action is refused with a 403 and a message, the request is left
  untouched, and the refusal is written to the audit trail.

What changed
  services/backend/app/api/requests.py  approve() and reject(): after the stage and role
                                      checks, refuse if target_employee_id is the caller
                                      (403 "You can't approve / reject a request that is
                                      about you (separation of duties).")
  services/backend/app/core.py        load_stage(): the same check, so IT "Process", the
                                      appointment step and both EUSS steps are covered too
  Audit                               new workflow event request_self_approval_blocked
                                      (outcome: denied, actor id in the details)
  README.md                           workflow section + audit table

Note
  Requests normally target role=employee, while approvers hold hr / director / aa /
  it_admin, so the target and the approver are never the same person in the seeded
  data. The check bites when a target's role changes after the request was raised. The
  demo therefore raises a request for an employee and then has the Administrator change
  that employee's role to HR.

Verification (manual, running stack)
  - `req` raised a grant request for erin; admin set erin's role to HR; erin signed in and
    saw the request in the HR queue.
  - Approve as erin -> 403 with the separation-of-duties message; request still pending_hr
    with no approved / rejected entry in its timeline.
  - Reject as erin -> same 403. (First attempt returned 500, UnboundLocalError: the check had
    been pasted twice and one copy ran before `status` was set. Fixed by keeping a single

  - `hr` (Harper) approved the same request normally, so legitimate approvers are not blocked.

[2026-11-08 SGT]  CHANGE 008 — HR system (HRMS): event-driven joiner / mover / leaver
-------------------------------------------------------------------------------
Summary
  New `hrms` container that stands in for the HR system of record (or ServiceNow HRSD).
  When HR records a hire, a transfer or a resignation there, it sends a signed webhook to
  the backend, which raises the matching onboard / shift / return request by itself. A
  resignation applies a kill switch first: the employee is suspended everywhere before the
  return workflow even starts.

What changed
  services/hrms/                      NEW container (port 8091, published on 127.0.0.1 only):
                                      UI to record hire / transfer / resign, keeps its own
                                      people + event record, sends the signed webhook, retries
                                      failed deliveries with the same event id, "Re-send" button
  services/backend/                   NEW POST /api/hr/events (signed webhook) and
                                      GET /api/hr/events (IT Admin, Admin); hr_events table so
                                      each event id is processed once; "HR System (Automated)"
                                      system actor (role system, cannot sign in); kill switch
                                      on resign; test_hr_events.py (offline checks)
  Audit                               hr_event_received, hr_kill_switch, hr_event_processed,
                                      hr_event_rejected, hr_event_failed,
                                      hr_event_signature_rejected
  docker-compose.yml                  hrms service; HRMS_WEBHOOK_SECRET passed to backend + hrms
  scripts/generate_secrets.py         new secret HRMS_WEBHOOK_SECRET
  README.md                           containers table, project structure, HR system section,
                                      API table

Webhook
  POST /api/hr/events
  X-HR-Timestamp: <unix seconds>
  X-HR-Signature: sha256=HMAC_SHA256(HRMS_WEBHOOK_SECRET, "<timestamp>." + body)
  A bad signature or a timestamp more than 5 minutes off is refused (401).

To apply

  docker compose up -d --build

[2026-11-01 20:45 SGT]  CHANGE 006 — Mandatory Job Rotation (MJR) tracker
-------------------------------------------------------------------------------
Summary
  Implements HR pain point "10) Mandatory Job Rotation" from the MND HR process review:
  HR no longer tracks each officer's rotation timeline by hand or drafts e-mails to
  Directors. The backend knows when each officer joined their department, flags them at
  the 4-year mark, e-mails the Directors, and records the Director's decision. "Rotate"
  hands the Requestor a pre-filled department shift request, so the move AND the change
  of access go through the existing approval workflow; the clock restarts when IT
  processes the shift. "Keep" needs a reason and comes back for review in 12 months.

How it works
  - employees.department_since: set when an onboard / shift is processed by IT, when an
    administrator moves someone directly, or corrected by the administrator by hand.
  - States: ok (within term) -> due_soon (90 days before) -> due -> kept (until review date,
    then due again) | rotation_planned -> shift_in_progress -> ok in the new department.
    A rejected shift puts the officer back to due.
  - Background loop (same thread as the Keycloak sync): hourly, and once at start-up, e-mails
    Directors (copy to HR) one summary of officers newly due; each officer once per cycle
    (employees.rotation_alerted_at). HR can also run it from the console.
  - Decisions in rotation_decisions (keep / rotate, reason, destination, review date,
    linked shift request). A shift request may carry rotation_decision_id; it is checked
    (right employee, current tenure, not already used) BEFORE anything is changed.
  - Audit (category workflow): rotation_due_notified, rotation_keep, rotation_rotate; the
    shift request's history notes "Mandatory Job Rotation, confirmed by Director";
    administrator date corrections appear in account_updated (old -> new).
  - Console: Director dashboard "Due for rotation" (Rotate / Keep) + "Rotation tracker";
    HR dashboard same lists read-only + "Check now & e-mail Directors"; Requestor dashboard
    "Rotations to raise" (pre-filled shift request); Administrator employee row "since" date.
  - Demo seed (relative to today, only fills empty values): alice 5y3m and frank 4y2m are
    due, grace 3y10m due soon, the rest within term. Existing databases: employees already
    in a department start from their last completed onboard / shift into it, else today.
  - Tunables (optional backend env): MJR_ROTATION_YEARS=4, MJR_DUE_SOON_DAYS=90,
    MJR_KEEP_REVIEW_MONTHS=12, MJR_CHECK_INTERVAL_SECONDS=3600.

  Review of CHANGE 004 against the "self-contained JWT" trade-off (tokens validated locally
  keep working while Keycloak is down, but cannot be cancelled early) found four gaps. All
  four are closed; the outage behaviour (backend keeps validating with cached keys,
  signed-in service users carry on) is deliberately kept.

Gaps and fixes
  1. A user disabled / signed out DIRECTLY in the Keycloak admin console (not via the
     ServiceJourney console) kept API access for up to 5 min, and Service1/2 sessions never
     ended (they only checked the backend DB, which still said "active").
     -> backend [kc_events.py]: Keycloak admin events that disable, delete or sign out a
        user, or reset / remove a credential, set employees.tokens_revoked_after to the
        event time (within ~10 s, one background cycle).
     -> services: every 60 s the session's refresh token is presented to Keycloak; a
        refusal ends the session. Keycloak unreachable = fail open (outage-tolerant).
  2. Service1/2 had no absolute session limit, and the 5-second status poll kept renewing
     the 30-min idle cookie, so a session could outlive the 8 h SSO maximum (Keycloak does
     not send back-channel logout when a session merely expires).
     -> services: idle 30 min counted from real page views only; absolute 8 h from sign-in;
        plus the Keycloak check above.
  3. Revoked Keycloak session ids were kept in memory while the session lived in the signed
     client cookie, so after a service restart a remotely signed-out cookie worked again.
     -> services: sessions now live server-side (cookie = random handle, like the console);
        a restart ends them, back-channel logout removes them.
  4. During a Keycloak outage, forced sign-out and password / 2FA reset failed before the
     backend-side revocation ran, and a role change / deactivation "sign out everywhere"
     was not retried.
     -> backend: tokens_revoked_after is set FIRST; forced sign-out queues the Keycloak
        logout (new employees.kc_logout_pending, retried every 10 s) and reports
        keycloak_synced=false; push(end_sessions=True) queues it too.
     -> /api/service/access accepts session_issued_at and answers reason "signed_out" for a
        service session older than tokens_revoked_after, so forced sign-outs reach
        Service1/2 even while Keycloak is down.

What changed
  Password storage
  - Argon2id hashing (argon2-cffi 23.1.0; t=3, m=64 MiB, p=4, per-hash salt), per the

  - 12-128 chars, spaces/Unicode allowed (NFKC), no composition rules, no forced expiry.

  - Account lock-out: 5 wrong passwords -> locked 15 min (password reset unlocks).
  - Per-client-IP rate limits: sign-in 20/min, MFA 20/min, forgot-password 5/15 min (HTTP 429).
  - Same error message and same timing (dummy Argon2 verify) for unknown users vs wrong
    passwords; forgot-password always answers the same and mails in the background.

  - Admin "Reset password": random temporary password shown once, user signed out.
  - Admin "Create account": blank password -> generated temporary one; chosen ones must pass

  - Console, service1, service2 authenticate to the backend with client credentials

    authenticated clients. Service logins get the identity but no console session.
  Secrets management
  - No secrets in docker-compose.yml any more. New scripts/generate_secrets.py writes strong

  - CSRF Origin/Referer check on every POST, idle-timeout cookie, X-Frame-Options DENY,

[2026-10-26 21:57 SGT]  CHANGE 001 — TOTP two-factor authentication (MFA)
-------------------------------------------------------------------------------
Summary
  Sign-in is now password + a 6-digit TOTP code (RFC 6238) from an authenticator
  app (Google/Microsoft Authenticator, Authy, 1Password, ...). TOTP is the default
  and only MFA method.

Policy
  - REQUIRED for staff roles: admin, requestor, hr, director, aa, it_admin, euss.
    They are forced to enrol (QR code) at their first sign-in and cannot turn it off.
  - OPTIONAL for ordinary employees: opt in/out from the console "Security" page.
  - Configurable with the backend env var MFA_REQUIRED_ROLES.

Behaviour
  - Login is two steps: /api/login (password) returns a 5-minute "mfa_token"
    challenge (NOT a session); /api/login/mfa (code) returns the session token.
  - 10 one-time recovery codes issued at enrolment (shown once, stored hashed,
    regenerable from Security with a current code).
  - TOTP secrets encrypted at rest (Fernet; key MFA_ENC_KEY or derived from SECRET_KEY).
  - Each 30 s code accepted once per account (replay protection, atomic in SQL),
    +/- 1 window for clock drift.
  - 5 wrong codes lock the second factor for 5 minutes.
  - Backend rejects any password-only session token for an account that requires
    or has enabled MFA (defence in depth, e.g. tokens issued before this change).
  - Administrator can reset a user's MFA (lost phone) from the dashboard "2FA" column.
  - New auth_events audit table (failed passwords, wrong codes, lock-outs, enrolments,
    recovery-code use, resets) shown to the admin as "Recent sign-in activity".
  - Personal Laptop (service1) and Account (service2) logins also ask for the code;
    un-enrolled staff are told to set up 2FA in the console first.
  - Passwords are still plaintext (unchanged, per POC requirements).
